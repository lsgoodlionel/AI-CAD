# 构件轮廓环自交 → 算量得 0 体积（实测·修复·边界）

> 2026-09-09 ｜ 代码：`core/model3d/ring_order.py`、`element_recognizer.py`
> ｜ 量测脚本：`scripts/model3d/column_outline_census.py`

## 1. 缺陷

`services/model_qto.py:_column_quantity` 用**鞋带公式面积** × 层高算柱混凝土
体积、用周长算模板面积，`_slab_quantity` 同理。轮廓若是自交环，鞋带面积
**恰好为 0** ⇒ 该构件混凝土量为 0、模板量失真。而 QTO 汇总经
`POST /projects/{id}/model/quantities/to-proposal` 喂进创效提案，
**是要走三审的经济数字**。

### 成因（两层，都已确认）

**根因在 `geometry_extractor._collect_pdf_drawings`**：填充路径按**线段绘制
顺序**逐段累加两端点（`path_points.extend([a, b])`）。子段首尾相接一路画
下来时它恰好等于环序，**子段乱序/反向时就不是**。极端情况一个矩形柱被画成
「底边 + 顶边」两条线段，点序 `[A, B, D, C]` 构成 8 字形。

**`_downsample_ring` 把坏环原样传下去**：它按索引顺序保点
（`[poly[i] for i in sorted(keep)]`），这个做法的前提是入参已是环序。
入参不是环序时，降点保不出环序；且降点还能把一个**本来正常的凹环**
采成自交环（凸环不会）。

坏环有两种形态，本次都覆盖：

| 形态 | 样子 | 判据（**无阈值**）|
|---|---|---|
| 穿越 | 8 字形 | 两条不相邻边在各自内部相交 |
| 回描 | `A→B→A→C` 原路折回 | 面积为 0 却在 x、y 两向都有真实跨度 —— 简单多边形不可能这样 |

## 2. 实测（先量后改）

样本：上海大歌剧院 structure + architecture 各图，`ORDER BY id LIMIT 120`。
**同一份代码、同一批图纸，只切换 `--no-repair` 开关**取两个数，
算量口径直接调下游 `services.model_qto.compute_quantities`。

| | 改前 | 改后 |
|---|---:|---:|
| 柱候选（点数 ≥ 3）| 3594 | 3594（**一个不多一个不少**）|
| └ 鞋带面积恰好为 0 | **694（19.3%）** | **0** |
| 板候选 | 373 | 373 |
| └ 鞋带面积恰好为 0 | 24（6.4%）| 2（0.5%）|
| 柱混凝土净体积 | 2,792.2 m³ | **5,820.8 m³（+108%）** |
| 板混凝土净体积 | 8,814,476.2 m³ | 8,824,214.6 m³（+0.11%）|
| 墙 / 梁 | 74,536.0 / 804.0 m³ | 不变 |

**换算过来：改前的柱混凝土量漏掉了 52%。**

构件数完全不变 —— 这条很要紧：修的是轮廓的点序，不是识别的收放，
所以不会顺带改变「识别出多少根柱」这个正交的指标。

体积是**抽样内逐图相加**，不是工程实际方量（同一层楼常有分区图/分幅图
多份，相加会重复计入）。**只有改前改后的相对差有意义**。板的绝对值
（8.8 百万 m³）本身就荒谬，那是既有的兜底板问题（见 CLAUDE.md 板 basis
一节），不在本次范围内。

### 零面积轮廓长什么样

- 点数分布 `{6: 9, 7: 685}` —— 本样本里**全部是降点后的输出**
  （`path_points` 恒为偶数，5/7 这类奇数只可能来自 `_downsample_ring`）。
- 包围盒 Top：`0.59×0.59`(65)、`1.97×1.97`(30)、`1.48×1.48`(18)
  —— **正是真柱那一档尺寸**，不是碎片。

> 与上游报告的差异：报告里那 407 个是 **4 个角点、包围盒 0.49×0.63**
> （未经降点的原生 4 点环，来自只有两条线段的填充路径）。
> 本样本命中的以 7 点降点环为主。**比率高度一致（18.6% vs 19.3%），
> 形态分布不同** —— 同一个机制的两种入口，不必强行对齐。

## 3. 修复

`core/model3d/ring_order.py`（纯函数、无依赖）：

- `is_self_intersecting(ring)` —— 严格穿越判定。**端点相接、共线相叠一律
  不算**，否则 `path_points` 的重复顶点（`[A,B,B,C,C,D,D,A]`）会让
  每一个正常轮廓都被误判成坏环。
- `repair_ring(ring)` —— 坏环按绕形心极角重排；**正常环一个点不动**。

接入三处（`element_recognizer.py`）：`_downsample_ring` 的两个出口
（覆盖柱 limit=8、设备 limit=12）、`_find_slabs` 直接吐 poly 的两个出口。
并在 `geometry_extractor` 的 `path_points` 处写明点序语义，
防止下一个消费方再假定它是环序。

### 为什么不用「面积/包围盒比例」当判据

细长斜置的真实构件（斜撑、斜墙段）面积本就远小于其轴对齐包围盒，
比例阈值必然误伤。上面两条判据是坏环的**精确特征**，无阈值、无误伤。

### 为什么不取凸包

凸包会丢点、把凹多边形（L 形 / T 形角柱）的面积抬高
（`dedupe.py` 实测外接矩形抬高约 27%）。极角重排**保留全部点**，
所以点数与轴对齐包围盒都不变 —— 这也是 `_downsample_ring` 那条历史教训
（曾把 728 根柱里 124 根存成碎条）的要求。

## 4. 能力边界（不要当成"恢复原形"）

- 极角序恢复的是**对形心的星形多边形**。源轮廓本就是凸的（矩形柱、
  圆柱的八边形近似 —— 占绝大多数）时这就是原形；源轮廓是**凹**的时候
  只能得到一个外扩的近似，**面积偏大** —— 但仍远好于原来的 0，
  且包围盒不变。点序信息在 `geometry_extractor` 那一步就已经丢了，
  这里无从还原真实的凹口。真要还原，得在提取端把子段串成环。
- **仍剩 2 个零面积板**（0.5%）：那是真退化（点沿一条直线共线），
  不是环序问题，重排也变不出面积，**不假造**。
- 穿越检测是 O(n²)，`MAX_CHECKED_POINTS = 256` 以上不查（回描判据是
  O(n)，不设上限）。实测轮廓远低于此上限，该门槛基本不触发。
- **这不是识别准确率**。与 `data/model3d/gold/CRITERIA.md` 的金标准判读
  是两回事：那里问「这个框算不算柱」（人工判读、有判据之争），
  这里问「已经吐出来的轮廓，环序在几何上是否成立」（纯确定性、无判读）。
  **两组数字不可混谈。**

## 5. 存量模型需要重建

修的是识别阶段。**已建好的场景里的坏轮廓不会自己变好**，
`model_qto` 读的是存量 `scene`。要让这 +108% 的柱混凝土量到达用户，
必须重跑建模。
